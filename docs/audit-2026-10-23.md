# CRM audit — 2026-10-23

Scope: caregivers, independent school-kindergarten schedules, Telegram role navigation/calendar, completion journal, filters, and Excel exports.

## Findings fixed

- Completion recording now takes shared row locks on the current lesson, child and specialist. Concurrent non-key edits must wait until the completion transaction finishes, preventing a record from being written against a lesson being reassigned during that transaction.
- Telegram webhook processing failures now return HTTP 503 instead of acknowledging success. Telegram can retry failed updates. Invalid organization IDs and rejected/inactive bot configurations remain ignored successfully.
- Added a regression test for webhook failure/retry behavior.

- Web lint, tests and production build passed.
- Isolated PostgreSQL-compatible PGlite tests applied the actual new migrations and exercised caregiver assignment/removal/deletion, persistent enrollment, duplicate lesson cards, schedule edits and child deletion cascades.
- Actual bot service exercised with PGlite and mocked Telegram transport: role contacts, own-contact validation, caregiver authorization revocation, separate internal/planner schedules, calendar, old parent confirmation flow, persistent menu message, Russian language and independent notifications.
- Completion integration: mark, duplicate request, undo, CRM correction, caregiver read-only check display, and retained journal snapshots after lesson/child deletion.

## Environment limit

Configured PostgreSQL at localhost:5432 was unavailable (`ECONNREFUSED` on both IPv4 and IPv6). Migration status could not be read and migrations were not applied to the configured database. No real Telegram messages were sent; live webhook reachability and real Telegram interaction remain unverified.

Before live acceptance testing, start/configure PostgreSQL, run `pnpm.cmd run migrate` in `api`, restart the API and serve the updated frontend. Confirm the existing Telegram bot configuration is active and its webhook points to the running API.

Deleted/reassigned lessons remain visible from journal snapshots; specialists can undo those historical checks while preserving event history. Future dates are read-only and marking is rejected in the service. Current lesson callbacks carry the expected child ID; pre-update callbacks are refreshed without applying changes. Isolated SQL/Telegram integration covers deleted-lesson display for caregivers and specialists, historical undo, a reassigned-child stale callback, and future navigation.
